# 架构

## 五层

```
     伴侣 app (SwiftUI)          app/
            │  只读 NDJSON，自己不碰 Steam、不碰文件
     JSON / NDJSON API           lib/api.py
            │  GUI 与 CLI 的唯一接缝
     一条龙编排                   bin/dryport
            │  查风险 → 下载 → 识别引擎 → 打包 → 入库
   ┌────────┼─────────┬──────────┬─────────┐
 风险闸   下载器     引擎识别    各引擎打包   入库
risk.py steam-     detect_    *-wrap.sh  steam-add.mjs
        download   engine()   unity-     shortcut-
        .mjs                  retarget/  mirror.py
```

## 数据流

1. **survey**（不下载任何游戏本体）：读 Steam 的 appinfo 与 depot 清单，算出每个游戏走哪条路线，
   落到 `SN_GAMES/route-all.json`（推的）与 `final-routes.json`（读真实清单确证的）。
   `api.py` 的 `all_routes()` 把两份合并，确证的优先，给每行打 `source` 字段。
2. **install**：风险闸 → 下载 → 识别 → 打包 → 入库。
3. **认出「已经装了」**：两个来源。steamcmd 下的目录带 `steamapps/appmanifest_<appid>.acf`；
   走已登录客户端下的没有 acf，认我们自己写的 `.dryport-appid`。
   打包好的 `.app` 认 `Contents/MacOS/steam_appid.txt`（`wrap_done()` 统一盖）。

## 下载为什么不用 steamcmd

`download_depot` 是 Steam 客户端控制台自带的命令，通过 CEF 远程调试口（`127.0.0.1:8080` 的
SharedJSContext）驱动已经登录的客户端，**不需要密码**。内容落在 `steamapps/content/` 这个暂存区，
Steam 不把它当「已安装」，所以碰不到用户已装的任何游戏。

两个实测坑：

- 落点是 Windows 风格的相对路径，在 macOS 上按 Steam 自己的 cwd 解析，实际落在
  `Steam.AppBundle/Steam/Contents/MacOS/steamapps/content/`，不是库根。两个候选路径都要找。
- 清单模式的过滤器 `sDepotDownloadFileFilter` 不清掉，内容会下成 0 个文件。

## 打包为什么按引擎分流

翻译层是有代价的：Rosetta 对 x86_64 游戏是死线（Apple 已宣布移除），Wine 的 D3D 层再好也过一道
翻译。而这些引擎本来就有官方 mac 版：RPG Maker 的游戏逻辑是 Ruby 脚本 + 资源，换个原生解释器就跑；
Unity Mono 的游戏逻辑是 IL，可尝试匹配的 mac 播放器与 Metal；2020.2 前的 mac 播放器仍为 x86_64，需要 Rosetta。
源游戏目录与生成副本分开；Unity 路线会改写副本的着色器与插件布局，不能宣称生成包内每个字节不变。

Steamworks 的扁平 API 在两个平台上导出名完全一样（Windows `steam_api64.dll` 与 macOS
`libsteam_api.dylib` 各 1042 个 `SteamAPI_*` 符号，逐个比对零差异），所以成就那条链路换壳后能直接接上。

## 游戏工作副本与恢复

翻译层最后考虑，优先使用匹配的原生引擎。单机游戏为兼容所需可以修改本机独立工作副本；Steam 客户端、已装游戏及下载原件保持不变。当前账号、许可、平台和风险检查照常执行，绝不修改或绕过反作弊与 DRM。这项授权不改变第三方运行时的来源、签名与许可证要求。

新适配沿用现有清单、克隆、暂存和排他发布能力，每个补丁须做到：

1. 绑定源版本与完整清单，留存未修改的原件副本或完整可验证备份，再生成独立工作副本。可用写时复制，不能用指向原文件的硬链接承载修改。
2. 核对预期输入后才应用补丁。记录补丁标识与实现摘要、原件及其留存副本的位置和摘要、输入与输出整体 SHA-256，以及每个增删改文件的相对路径和前后 SHA-256；不存在的一侧记为 null。生成文件另记来源和用途。
3. 回读原件及留存副本，要求与基线一致；工作副本的实际差异必须与补丁记录相符。完成签名与回读后才发布到新位置，失败保留暂存现场，不覆盖已有 app。
4. 恢复时从留存原件重新生成独立工作副本，核对清单回到原始基线；已有产物保留。恢复不覆盖、迁移或删除用户存档，存档位置须与待替换副本分开处理。

原件未变、补丁差异已记录、恢复通过、真实可玩分别验收。旧的原包直读实验保留原条件和结果；现有 Unity 等路线尚未全部补齐变更清单及恢复验证，不能因新增约定就宣称完成。项目只分发自有源码、补丁逻辑和必要元数据，不分发原游戏或改后游戏包。

## 实现语言

按实际瓶颈、维护成本和验证结果选择 Python、Rust 等工具。保留有效的 Python 编排与库；有测量证据的热点再评估 Rust 等实现，并对照相同功能的耗时、内存与输出。语言选择服务于体验和效率，不要求全面重写。

## 三个根目录

见 `lib/paths.sh` 的注释。要点：仓库可以 clone 到任何地方；十几 GB 的第三方运行时和
含个人数据的库表都在仓库外面，靠 `SN_RUNTIMES` / `SN_GAMES` 指过去。

## 只读库快照

GUI 启动调用 `api.py snapshot`，同一次读取返回 library 和 state。浏览库、详情与体检不再写 installed.json；安装等变更操作才显式更新。只有存在 `.app` 的记录算已安装，下载目录仍保留但不显示可启动。风险结果单独在详情检查，安装前 CLI 再检查一次。
